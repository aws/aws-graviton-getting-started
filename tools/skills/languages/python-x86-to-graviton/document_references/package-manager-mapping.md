# Package Manager Mapping

Python projects use many package managers, but every one of them can produce a **flat list of pinned requirements**, and one probe ([wheel-verification.md](wheel-verification.md)) then decides each pin. This file maps each manager onto that path so the phase documents only ever reference pip commands.

Two tiers:

- **Inline** (covered step by step in the phase docs, executed on the fixture variants while writing this skill): pip with `requirements*.txt`/`constraints.txt`, pip-tools, PEP 621 `pyproject.toml` with setuptools, uv, Poetry, conda/mamba.
- **Mapped** (route onto the pip path using the table in section 3; export command verified against upstream documentation or a scratch run): Pipenv, PDM, Hatch, vendored `site-packages` and Lambda layers.

The tiering follows adoption data: in the [Python Developers Survey 2024](https://lp.jetbrains.com/python-developers-survey-2024/) (PSF and JetBrains, more than 30,000 respondents) 74% use pip, 20% Poetry, 18% Conda, 12% uv (its first year), 9% pip-tools, 8% Pipenv; dependency files are `requirements.txt` 59%, `pyproject.toml` 36%, `setup.py` 16%. Among data-science respondents 27% install from Anaconda. PyPI download counts (pypistats.org, trailing 30 days at the time of writing) put uv at 123M, poetry 41M, pip-tools 12M, pipenv 12M, hatch 7M, pdm 5M.

Tool versions used for the executed checks: pip 26.2.1, uv 0.12.21, Poetry 2.5.1 with poetry-plugin-export 1.10.1, pip-tools 7.6.1, conda 26.7.2 (Miniforge, libmamba solver), conda-lock 4.0.2, Pipenv 2026.8.0, PDM 2.29.2.

## 1. Detection

Check for these files in the project root and in each package of a monorepo. A project may use more than one (a `pyproject.toml` plus a `requirements.txt` for deployment is common); record all of them in `01-project-assessment.md` and treat the one the deployment actually installs from (Dockerfile `RUN pip install ...`, CI, Makefile) as authoritative.

| Manager | Markers | Lock file | Lock is cross-platform? |
|---|---|---|---|
| pip | `requirements.txt`, `requirements-*.txt`, `requirements/*.txt`, `constraints.txt` | none, or a hashed requirements file | No: a hashed file carries only the hashes it was generated with (see section 2.1) |
| pip-tools | `requirements.in` or `*.in` next to a compiled `*.txt` with a `# This file is autogenerated by pip-compile` header | the compiled `.txt` | Yes when compiled with `--generate-hashes` (records every published file's hash; verified: 36 hashes for numpy 1.26.4 including the aarch64 wheel) |
| setuptools / PEP 621 | `pyproject.toml` with `[project]` and no lock; `setup.py`; `setup.cfg` | none | n/a |
| uv | `uv.lock`; `[tool.uv]` in `pyproject.toml`; `.python-version` | `uv.lock` | Yes (verified: 26 `aarch64` wheel entries in the fixture lock) |
| Poetry | `poetry.lock`; `[tool.poetry]` in `pyproject.toml` | `poetry.lock` | Yes (verified: 80 `aarch64` entries in the fixture lock) |
| conda / mamba | `environment.yml` (or `.yaml`), `conda-lock.yml`, `*.conda-lock.yml`, `conda-linux-64.lock` explicit files | `conda-lock.yml` is multi-platform; `conda list --explicit` output is single-platform (header `# platform: linux-64`) | conda-lock yes; explicit files no |
| Pipenv | `Pipfile`, `Pipfile.lock` | `Pipfile.lock` | Yes (hashes of all files; verified the numpy aarch64 wheel hash is present) |
| PDM | `pdm.lock`; `[tool.pdm]` in `pyproject.toml` | `pdm.lock` | Yes (verified: 14 `aarch64` entries in a scratch lock) |
| Hatch | `[tool.hatch.envs.*]` in `pyproject.toml` or `hatch.toml` | optional `pylock.toml` / `pylock.<env>.toml` when `locked = true` (PEP 751; written by the `pip` or `uv` locker) | depends on the locker; treat like a pip requirements file |
| Vendored | committed `site-packages/`, `vendor/`, `lib/`, `python/` (Lambda layer layout), `*.zip` layers | none | n/a: committed binaries are for one architecture |

Interpreter detection (needed for the probe's `--python-version`/`--abi`), in order of authority: Dockerfile `FROM python:3.X` or a distro image whose default Python is known; `.python-version` (pyenv, uv); `requires-python` in `pyproject.toml`; `[requires] python_version` in `Pipfile`; `python=3.X` in `environment.yml`; `runtime: python3.X` in a SAM/serverless template; CI configuration. Record the source of the decision.

## 2. Inline Tier: Command Matrix

All commands below were executed on the fixture variants used to build this skill unless marked "docs". Replace `3.11`/`cp311` with the project's interpreter.

### 2.1 pip (requirements files)

| Step | Command | Notes |
|---|---|---|
| Flat pins | the file itself. Resolve unpinned or ranged entries first: `python3 -m pip install --dry-run --ignore-installed --report graviton-validation/raw/requirements-report.json -r requirements.txt` then extract `name==version` from `install[].metadata` | `--dry-run --report` (pip >= 22.2) resolves without installing |
| Dependency tree | `pip install --dry-run --report`: `install[].requested` is `true` for direct dependencies, `false` for transitives | pip has no tree command; `pipdeptree` is a third-party package and needs an installed environment |
| aarch64 probe | `pip download --only-binary=:all: --platform manylinux2014_aarch64 ... --python-version 3.11 --implementation cp --abi cp311 <pin>` per pin, or the whole file at once with `pip install --dry-run --only-binary=:all: --platform ... --target /tmp/probe -r requirements.txt` | see wheel-verification.md sections 3 and 8 |
| Hash lock check | `pip install --dry-run --ignore-installed --only-binary=:all: --require-hashes --platform manylinux2014_aarch64 --platform manylinux_2_17_aarch64 --python-version 3.11 --implementation cp --abi cp311 --target /tmp/probe -r requirements-locked.txt` | fails with `THESE PACKAGES DO NOT MATCH THE HASHES` when only x86_64 hashes are present |
| Pin / override | edit the pin in `requirements.txt`; for a transitive, add it to a `constraints.txt` passed with `-c constraints.txt` (constraints pin without installing) | executed: `-c` with `msgpack==1.1.0` while installing `blosc2==0.6.4` resolved msgpack 1.1.0 |
| Regenerate hashes | `python3 -m pip hash --algorithm sha256 <aarch64 wheel>` and append a second `--hash=` to the line, or switch the file to pip-tools (below) | hand-made locks need every platform's hash listed |
| Install / test | `pip install -r requirements.txt` (plus `--require-hashes -r requirements-locked.txt` if present); tests per the project (`pytest`, `python -m unittest`, `tox`, Makefile target) | use `python.test_command` from `skill-config.md` if set |

### 2.2 pip-tools

| Step | Command | Notes |
|---|---|---|
| Flat pins | the compiled `requirements.txt`; the `.in` holds the human intent | compiled file has the `pip-compile` header |
| Tree | annotations in the compiled file (`# via <parent>`) give provenance for every transitive | |
| aarch64 probe | pip probe on the compiled file | `pip-compile` has **no** `--platform`/`--python-version` option (verified against `pip-compile --help`): it resolves for the interpreter it runs on. The platform-aware alternatives are `uv pip compile --python-platform aarch64-manylinux_2_<N>` with N from the target's glibc (section 2.4) or compiling on the ARM64 target |
| Pin / override | edit the `.in` (direct) or add the transitive to the `.in` with a comment; recompile | |
| Regenerate | `pip-compile --generate-hashes --output-file requirements.txt requirements.in` | executed: output carried 36 hashes for numpy 1.26.4, both the x86_64 (`666dbfb6...`) and aarch64 (`7ab55401...`) wheel hashes, so a pip-tools lock with hashes is already Graviton-safe; a lock **without** `--generate-hashes` has no hashes and is also fine |
| Install / test | `pip-sync requirements.txt` or `pip install -r requirements.txt` | |

### 2.3 setuptools / PEP 621 `pyproject.toml` without a lock

| Step | Command | Notes |
|---|---|---|
| Flat pins | read `[project].dependencies`, `[project.optional-dependencies]`, `[dependency-groups]` with the standard library: `python3 -c 'import tomllib; d=tomllib.load(open("pyproject.toml","rb")); print("\n".join(d["project"]["dependencies"]))'` (Python >= 3.11; `pip install tomli` on older interpreters) | executed on the fixture: 11 direct pins. Do **not** rely on `pip install --dry-run .`: it must build the project first and fails on layouts setuptools cannot auto-discover (fixture: `Multiple top-level packages discovered in a flat-layout`) |
| `setup.py` / `setup.cfg` | `install_requires` in `setup.cfg` is plain text; for `setup.py`, `python3 setup.py --help` cannot list deps reliably, so run `pip install --dry-run --report` on the project or read the file | ranges, not pins: resolve with `--dry-run --report` |
| Tree / probe | `pip install --dry-run --ignore-installed --only-binary=:all: --report <file> --platform manylinux2014_aarch64 ... --target /tmp/probe -r <extracted-list>` | executed: first blocker reported was `blosc2==0.6.3 (from versions: 0.6.4, ...)`; fix, re-run, repeat |
| Pin / override | edit `[project].dependencies`; transitive pins go in a `constraints.txt` consumed by the install command, or `PIP_CONSTRAINT=constraints.txt` in the Dockerfile | PEP 621 has no override table |
| Install / test | `pip install .` (builds the project and its extensions on the target architecture; see phase 2.1 for extension flags), `pip install -e .[dev]`; tests per project | |

### 2.4 uv

| Step | Command | Notes |
|---|---|---|
| Flat pins | `uv export --no-dev --format requirements.txt -o graviton-validation/raw/requirements-resolved.txt` (add `--no-hashes` for the probe input) | executed; output lists every locked package with `--hash` lines for all files |
| Tree | `uv tree --no-dev` | executed |
| aarch64 probe | native: `uv pip compile --python-platform aarch64-manylinux_2_34 --python-version 3.11 --only-binary :all: --no-deps requirements-resolved.txt > /dev/null`; or the pip probe on the export | executed: `Because blosc2==0.6.3 has no usable wheels and you require blosc2==0.6.3, we can conclude that your requirements are unsatisfiable.` Use the highest platform value not above the target's glibc (Phase 1.1): uv 0.12.21 accepts `aarch64-manylinux_2_17`, `_2_28` and `_2_31` to `_2_40` (and `aarch64-unknown-linux-musl`), so Amazon Linux 2023 takes `_2_34` and Amazon Linux 2 `_2_17`. With `_2_17`, polars 1.0.0 (`manylinux_2_24`) and confluent-kafka 2.15.1 (`manylinux_2_28`) fail although Amazon Linux 2023 accepts both; wheels between two values (polars 1.0.0 on Amazon Linux 2) need the pip probe. Keep the output on stdout: with `-o /dev/null`, uv exits 2 with `Permission denied` whenever the resolution succeeds |
| Pin / override | direct: edit `[project].dependencies`; transitive: `[tool.uv] override-dependencies = ["msgpack==1.1.0"]` (replaces the requirement) or `constraint-dependencies = [...]` (narrows it) | executed: override produced `msgpack 1.1.0` in the regenerated lock |
| Regenerate | `uv lock` | executed after changing `blosc2==0.6.3` to `0.6.4`: lock gained the `blosc2-0.6.4-...manylinux2014_aarch64.whl` entry |
| Install / test | `uv sync --frozen` (or `uv pip install -r requirements.txt` for pip-style projects); `uv run pytest` | `uv sync` installs for the running platform, so run it on ARM64 in phase 3. Executed natively on Graviton with the fixture's regenerated `uv.lock`: uv fetched `cpython-3.11.9-linux-aarch64-gnu` to match `.python-version`, installed every package from the lock, and the tests passed |

### 2.5 Poetry

| Step | Command | Notes |
|---|---|---|
| Flat pins | `poetry export --format requirements.txt --without-hashes --output graviton-validation/raw/requirements-resolved.txt` | `export` is a **plugin** in Poetry 2.x: a bare install reports `The requested command export does not exist` (verified). Install with `poetry self add poetry-plugin-export` (or, when Poetry itself is a uv tool, `uv tool install poetry --with poetry-plugin-export`). Exported lines carry environment markers (`; python_version >= "3.11"`); keep them and run the Phase 1.3 probe with the project's interpreter, which evaluates them (executed: the fixture's Poetry and uv exports gave the same `MUST UPGRADE` and `CHECK SDIST/ABI` verdicts as its pip variant) |
| Tree | `poetry show --tree` | executed; shows `mkl` pulling `intel-openmp`, `tbb`, `onemkl-license` |
| aarch64 probe | pip probe on the export | `poetry install` resolves for the running platform only; there is no target-platform flag |
| Pin / override | direct: edit the dependency in `pyproject.toml`; transitive: Poetry has no override table, so add the package as an explicit dependency with the needed constraint (`poetry add --lock "msgpack==1.1.0"`) and document why | executed; `poetry add --lock` wrote `"msgpack (==1.1.0)"` to `[project].dependencies` and the lock |
| Regenerate | `poetry lock` | executed after the blosc2 pin change: 4 `blosc2-0.6.4-*aarch64*` entries in the new lock. By default `poetry lock` does not update packages already in the lock file; `poetry lock --regenerate` rebuilds it from scratch (Poetry CLI docs) |
| Install / test | `poetry sync` (in Poetry 2.5.1, `poetry install --sync` is marked deprecated), `poetry run pytest` | executed natively on Graviton with the fixture's regenerated `poetry.lock` (`poetry install --all-extras`): the tests passed; the environment's compiled packages sat in `lib64/.../site-packages` |

### 2.6 conda / mamba

conda packages and pip packages inside the same environment are different worlds: conda resolves against channel subdirectories (`linux-aarch64` for Graviton), pip resolves against PyPI wheels. Treat the two sections of `environment.yml` separately.

| Step | Command | Notes |
|---|---|---|
| Flat pins (conda section) | the `dependencies:` list; for an existing environment `conda env export --from-history` gives the requested specs, `conda list --explicit` the exact single-platform URLs | executed; explicit output header shows `# platform: linux-64`, so an explicit file produced on x86 cannot be replayed on Graviton |
| Flat pins (pip section) | the `- pip:` sub-list is ordinary pip pins: extract it and resolve its transitives with the block below this table | executed: extraction yielded `blosc2==0.6.3, pygeos==0.14, docopt==0.6.2, six==1.11.0, requests==2.32.3`; resolved alone, pip chose numpy 2.4.6 for blosc2, and with the conda pin `numpy==1.26.4` as a constraint it kept 1.26.4. The probe then flagged blosc2 and pygeos, as in the pip variant |
| Tree | `conda list -p <env>` with the channel column: `pypi` marks pip-installed packages | |
| aarch64 probe (conda section) | `CONDA_SUBDIR=linux-aarch64 conda create -n probe --dry-run --json -c conda-forge --override-channels <specs>` or `CONDA_SUBDIR=linux-aarch64 conda env create --dry-run -f environment.yml -p /tmp/probe --json` | executed: `mkl=2024.2.2` fails with `PackagesNotFoundInChannelsError ... not available from current channels`; without mkl the solve succeeds and `numpy=1.26.4` links against `libopenblas` on `linux-aarch64`. The `--dry-run` does not evaluate the `pip:` section. Set `CONDA_OVERRIDE_GLIBC` to the target's glibc (Phase 1.1): otherwise the solver assumes the analysis host's (`conda info` reports `__glibc=2.34` on the Amazon Linux 2023 host, `2.26` with `CONDA_OVERRIDE_GLIBC=2.26`) |
| Pin / override | edit the spec in `environment.yml` (`numpy=1.26.4`); conda has no transitive override: pin the transitive explicitly in the file | |
| Regenerate (multi-platform lock) | `conda-lock -f environment.yml -p linux-64 -p linux-aarch64 --lockfile conda-lock.yml` | executed (without mkl): lock contains both platforms, numpy entry with `platform: linux-aarch64`. `conda-lock` is a separate tool (`uv tool install conda-lock` or `pip install conda-lock`) |
| Install / test | `conda env create -f environment.yml` on the ARM64 host (Miniforge `Miniforge3-Linux-aarch64.sh` per [python.md section 2.7](https://github.com/aws/aws-graviton-getting-started/blob/main/python.md#27-graviton-support-in-conda--miniforge)); `conda run -n <env> pytest` | the repo recommends Miniforge/conda-forge; Anaconda's `defaults` channel also publishes `linux-aarch64` ([isv.md](https://github.com/aws/aws-graviton-getting-started/blob/main/isv.md)). Executed natively on Graviton (Miniforge 26.7.2): the fixed `environment.yml` gave conda-forge numpy 1.26.4 on `libopenblas` with blosc2 and shapely from the pip section, and the tests passed |

Resolve the pip section with the conda-side pins as constraints (`-c`), so pip does not choose its own versions of packages conda already provides. Run it in the project-version environment from Phase 1.1. A constraint only applies to the PyPI project of the same name, so rename any pin whose conda package name differs from its PyPI name:

```bash
mkdir -p graviton-validation/raw
awk '/^[[:space:]]*- pip:[[:space:]]*$/ {f=1; ind=index($0,"-"); next}
     f { if (index($0,"-") <= ind || $0 !~ /^[[:space:]]*-/) {f=0; next}
         sub(/^[[:space:]]*-[[:space:]]*/, ""); print }' environment.yml > graviton-validation/raw/conda-pip-section.txt
awk '/^dependencies:/ {f=1; next} f && /^[[:space:]]*- pip:/ {exit}
     f && /^[[:space:]]*- [A-Za-z0-9_.-]+=[0-9]/ {sub(/^[[:space:]]*- /, ""); split($0, a, "=");
       if (a[1] != "python" && a[1] != "pip") print a[1] "==" a[2]}' environment.yml > graviton-validation/raw/conda-constraints.txt
python3 -m pip install --dry-run --ignore-installed -q --report graviton-validation/raw/dependency-tree-pip-section.json \
  -c graviton-validation/raw/conda-constraints.txt -r graviton-validation/raw/conda-pip-section.txt
python3 - <<'EOF'
import json
r = json.load(open("graviton-validation/raw/dependency-tree-pip-section.json"))
with open("graviton-validation/raw/requirements-resolved.txt", "w") as out:
    for i in r["install"]:
        kind = "direct" if i.get("requested") else "transitive"
        out.write(f"{i['metadata']['name']}=={i['metadata']['version']}  # {kind} via environment.yml pip section\n")
print(len(r["install"]), "pins")
EOF
```

Then run the Phase 1.3 probe on `requirements-resolved.txt`.

Channel note: the conda-forge `linux-aarch64` subdirectory exists and is populated (`https://conda.anaconda.org/conda-forge/linux-aarch64/repodata.json.zst` returns HTTP 200). A package missing there is a conda finding; the pip-probe rules do not apply to it.

## 3. Mapped Tier: Route onto the pip Path

| Manager | Detect | Export flat pins | Then | Verified how |
|---|---|---|---|---|
| Pipenv | `Pipfile`, `Pipfile.lock` | `pipenv requirements > requirements-resolved.txt` (add `--hash` to include hashes, `--dev` for dev packages) | pip probe on the export; pin changes go in `Pipfile` followed by `pipenv lock`; no override table, so pin transitives explicitly in `[packages]` | scratch run with Pipenv 2026.8.0: `pipenv lock` then `pipenv requirements` printed `blosc2==0.6.3 msgpack==1.2.3 numpy==1.26.4 requests==2.32.3`; `Pipfile.lock` stores hashes for all 36 numpy 1.26.4 files, including the aarch64 wheel, so it is Graviton-safe once regenerated after a pin change |
| PDM | `pdm.lock`, `[tool.pdm]` | `pdm export --without-hashes -f requirements -o requirements-resolved.txt` | pip probe; direct pins in `[project].dependencies`; transitive overrides in `[tool.pdm.resolution.overrides]` (`asgiref = "3.2.10"`, from the [PDM dependency docs](https://pdm-project.org/latest/usage/dependency/)); regenerate with `pdm lock` | scratch run with PDM 2.29.2: `pdm lock` produced a lock with 14 `aarch64` file entries; `pdm export` printed the four pins |
| Hatch | `[tool.hatch.envs.*]`; optional `pylock.toml` when `locked = true` | dependencies live in `[project]` plus per-environment `dependencies = [...]`: extract with `tomllib` as in section 2.3 and append the env lists; if a `pylock.toml` exists, `pip install --dry-run --report -r pylock.toml` (pip >= 26.1 reads PEP 751 lock files, experimental per pip's changelog) | pip probe; pins edited in `pyproject.toml`; `hatch env create` regenerates `pylock.toml` | [Hatch environment docs](https://hatch.pypa.io/latest/config/environment/overview/): `locked`, `locker` (defaults follow the environment's installer), `lock-filename`, default `pylock.toml`/`pylock.<ENV_NAME>.toml`; pip changelog 26.1 (2026-04-26) "experimental support to read requirements from standardized pylock.toml files". Executed with Hatch 1.18.1: with `installer = "uv"` the lock was written and the environment created; with the default pip installer the lock was written, then `hatch env create` stopped at "lockfiles with the pip locker is not yet supported". With `skip-install = true` the lock held only the environment's own dependencies, not `[project]`'s, so extract `[project]` with `tomllib` as well; pip 26.2.1 read `-r pylock.toml` with an experimental-feature warning |
| Vendored `site-packages` / `vendor/` | committed `*.so`, `*.dist-info`, `*.egg-info` under a vendor directory | `ls vendor/*.dist-info` (or `*.egg-info`) gives `name-version`; write them as `name==version` | pip probe on those pins to find aarch64 wheels, then re-vendor on ARM64 or with `pip download --platform manylinux2014_aarch64 --only-binary=:all:`; committed x86 `.so` files are always MUST UPGRADE (phase 1.2) | fixture: `file vendor/*.so` reports `ELF 64-bit LSB shared object, x86-64` |
| Lambda layers | `python/` at the zip root (`python/lib/python3.X/site-packages/` when built from a venv), SAM/CloudFormation `Layers:`/`ContentUri`, `serverless.yml` | same as vendored: enumerate `*.dist-info` inside the layer | re-create the layer for arm64 with the Phase 2.1 block, which offers the wheel tags of the function runtime's glibc, and set `Architectures: [arm64]` on the function (only if the project already ships the template, phase 2.4) | [AWS Lambda Python layers](https://docs.aws.amazon.com/lambda/latest/dg/python-layers.html): layer packages go in `python/` at the zip root; the doc shows the `--platform manylinux2014_x86_64 --only-binary=:all: -t python/` pattern, which the migration mirrors with the aarch64 tags for the runtime's glibc (Phase 1.1); the repo's [aws-lambda/README.md](https://github.com/aws/aws-graviton-getting-started/blob/main/aws-lambda/README.md) says to check binaries in dependencies, layers, and extensions |

When a project uses a manager not listed anywhere here, apply the same recipe: find the lock or manifest, produce `name==version` lines, run the pip probe, and make pin changes through the manager's own mechanism so its lock stays consistent. Record the manager and the commands used in `01-project-assessment.md`.

## 4. Rules That Apply to Every Manager

1. **Never switch managers.** A pip project stays a pip project; "move to uv" is out of scope ([agent-scope-boundaries.md](agent-scope-boundaries.md)).
2. **Change pins through the manager, then regenerate its lock.** Editing `poetry.lock` or `uv.lock` by hand, or leaving a lock stale after a `pyproject.toml` edit, produces an install that ignores the fix or refuses to run.
3. **A lock generated on x86 is only a problem when it is architecture-specific.** `poetry.lock`, `uv.lock`, `pdm.lock`, `Pipfile.lock`, pip-tools output with `--generate-hashes`, and `conda-lock.yml` with a `linux-aarch64` platform are cross-platform. Hand-hashed requirements files and `conda list --explicit` files are not.
4. **Probe the pins the deployment installs**, not every file in the repository. If the Dockerfile installs `requirements.txt` and `pyproject.toml` only exists for packaging, `requirements.txt` decides.
5. **The interpreter is part of the probe.** Export and probe with the project's `--python-version`/`--abi`; a different interpreter yields a different answer (wheel-verification.md section 6).
